# Kanban – feature/fe-expansion (028)

**Theme:** Frontend expansion & UX deep dive for the mapping workbench  
**Branch:** `feature/app/FE-028-expansion`  
**Goal:** Turn the existing HTMX + Tailwind workbench into a richer client that surfaces more of the monorepo’s capabilities (analytics, dataset control, eval orchestration, observability) while keeping the view architecture clearly modularized.

> Status: **INPROGRESS**  
> Branch target version: `Unreleased`  
> Introduced in: `v0.1.0`  
> Last updated in: `v0.1.0`

---

## Background

The initial web workbench (REFR-027) reorganized `views/` but still exposes only a small slice of the pipeline: mapping entrypoints, metric snapshots, and eval toggles. The monorepo already ships capabilities that the UI could expose (analytics drilldowns, dataset store management, evaluation reports, NoMatch remediation, compliance insights, etc.). 028 pushes the frontend toward a “command center” that mirrors the CLI/API feature set.

## Acceptance criteria

1. Frontend directory layout is documented and enforced (lint or dev docs).  
2. Mapping/workbench UI exposes history, validation status, and NoMatch remediation.  
3. Analytics/observability pages surface metrics, filters, and export options matching backend capabilities.  
4. Eval control center supports dataset browsing, run scheduling, and result comparisons.  
5. Accessibility, docs, and automated UI tests cover the new experiences.

---

## Risks & mitigations

- **Scope creep** – Many sub-features; use the kanban sections above to land incremental PRs (architecture → mapping → analytics → eval → docs).  
- **Backend gaps** – Some UI toggles may require new API endpoints; coordinate with API owners before exposing controls.  
- **HTMX fragmentation** – Ensure fragments cache/invalidate correctly; add integration tests where possible.  
- **Design consistency** – With more components, adopt Storybook route + design tokens to avoid drift.
